## Config shape (as settled)
```json
{ "id": "billing", "kind": "items", "label": "Billing", "...": "...",
  "entry": {
    "actions":  [ { "id": "added", "label": "Added", "fragment": "{action} {qty} {item} {details}" } ],
    "items":    [ { "id": "item1", "label": "Item 1 (placeholder)" } ],
    "outcomes": [ { "id": "completed", "label": "Completed", "fragment": "- completed." },
                  { "id": "requested", "label": "Requested — not yet completed", "fragment": "- requested, not yet completed." },
                  { "id": "unable", "label": "Unable to complete", "fragment": "- unable to complete." } ],
    "outcomeRequired": true, "qty": false, "details": true } }
```
(The file holds the literal em dash, not `—`.) `entry.actions[]`/`outcomes[] {id, label, fragment}`, `entry.items[] {id, label}`, booleans `qty`, `details`, `outcomeRequired` (all optional, default false; `outcomes` optional unless `outcomeRequired`). Fragment placeholders: `{action} {item} {qty} {details} {outcome}` (the entry's own, substituted by the model) plus the context ones (`{tech.firstName} {tech.name} {tech.id} {job.number} {job.workOrder} {address}`, filled by the composer); anything else is a schema **warning** (and stays as typed in the note).
Entry text = the action's `fragment`, a space, then the chosen outcome's `fragment`; the composer then squeezes spaces, capitalises the first letter and adds the end full stop.
Equipment defaults: actions Added/Removed/Swapped, each `"{action} {qty} {item}. {details}"`; 5 items `item1..item5` labelled `Item N (placeholder)`; qty on, details on, no outcomes, `outcomeRequired` false.
Billing defaults: actions Added/Removed/Changed, each `"{action} {qty} {item} {details}"`; the same 5 items; the three outcomes above; `outcomeRequired` true, qty off, details on.
Session entry: `{action, item, qty, outcome, details}` (strings, ids not labels); snapshot: `categories.<id>.entries = [{action,item,qty,outcome,details}, ...]`.
Example, Equipment "Swapped" + Item 1 + qty 2 + details "Needs cable": `Swapped 2 Item 1 (placeholder). Needs cable.`; Billing "Added" + Item 2 + Completed: `Added Item 2 (placeholder) - completed.`

## Decisions where the plan was silent
1. **Where the typed text goes**: the model substitutes the five placeholders in ONE pass over the template. The composer scans every fragment again, so a typed value containing `{` is not put into the fragment; the fragment gets a private placeholder (`{itemsDetails3}`, index = position in the list) and the text goes into `Values`, which the composer inserts without expanding. Text without `{` is inserted directly, so the raw fragments stay readable (and exact in tests). Same rule for labels.
2. **Duplicate = same printed sentence** (lower case, after squeeze/capital/end punctuation), not just identical fields. That is what the composer would drop silently, so the second one is refused: `That entry is already in the list <em dash> change the quantity instead` (no final stop). Consequence: in Billing (no qty) a different qty is also "the same entry".
3. **qty / details switched off** (`qty:false`): the value is emptied by `Clean`, not validated, never printed. This is also how Billing ignores a qty.
4. **Quantity box**: a plain text box (`ax-text`), not the library's number box, because a number box cannot be empty (it shows 0 and clamps); empty = "no quantity". Valid = digits only, 1-99, written canonically (`007` -> `7`). Placeholder "Leave empty if not needed".
5. **Control choice**: action and outcome are segmented controls when there are at most 4 options and at most 60 label characters in total, otherwise a radio list; item is a drop-down (`ax-dropdown`, "Choose an item").
6. **Stored entries with ids the config no longer has** are skipped by `Fragments` with a warning (ids and positions only) and shown in the list as "This entry uses an option that is no longer available." with only a Remove button. Missing outcome on an old entry (outcome became required) is kept, printed without an outcome, plus a warning: the note never claims "completed" for it.
7. **A category stays "used"** after all its entries are removed (same as "Reset this category" in M5: stats keep the credit, the rail dot stays, the note just has no line for it).
8. **A refused add** (missing part, duplicate) changes nothing, not even "used" or the stats.
9. **Hints** (`Choose an action.` / `Choose an item.` / `Choose an outcome.` / `Quantity must be a whole number from 1 to 99 (or leave it empty).`) appear after Add/Save was pressed with something missing, update live while the form changes, and clear on success. The duplicate message is a separate line under the form.
10. **Form state lives in the view** (`this.Form`), is written to the text boxes on edit/clear, and read back by `Flush()` (called with the other flushes before Copy / Clear All / History). Re-render policy as in StepsView: controls rebuilt only when their structure (lists, labels, flags) changes or on a forced refresh; a focused text box is never overwritten. New call, Clear All, History load and config change clear the form.
11. **Copy Notes**: steps categories are checked first (M5 rules), then each items form in page order. A "draft" is any action/item/outcome/qty/details in the form that is not in the list, or, while editing, a difference from the stored entry. `"<Label> has an entry that wasn't added. Copy without it?"`: Yes copies (the question is asked once per category with a draft), No goes to that page and stops. Nothing else (Clear All, new call, History) is ever blocked.
12. **Styling**: the entry sentence in the list and the preview come from `ItemsModel` with the note template's `sentenceCase`/`endPunctuation` (copied in `App.ModelFor`), so what you see is what the note prints (`{tech.*}` placeholders in a fragment are shown unfilled in the preview).
13. **Billing details position**: the action fragment holds `{details}`, so typed details come before the outcome text (`Changed Item 4 (placeholder) <details> - unable to complete.`). If you prefer them last, move `{details}` to the end of the outcome fragments.
14. **Schema strictness**: `fragment` must be present (may be `""`) on every action and outcome; items have only `id`/`label`; unknown keys inside `entry` and unknown `{placeholders}` in fragments are schema warnings (reported by `Schema.Validate`, for the Admin app later; the config store does not turn them into the title-bar chip), everything else listed is an error.
15. **MoveEntry** exists in the session/App (tested) but has no buttons in the UI yet.
16. **`Map.Delete` throws** for a missing key. Found while resetting a category without fragments; `CallSession.Drop` guards it (also in `ApplyEngine`).
17. The M4 selftest used dev sample fragments in Equipment/Billing; it now puts them straight into the session (`MainWindow.SelfSample`) because items categories no longer take dev samples. Log keys are unchanged.

## Filling in the placeholder text
Edit `config\config.json` (a copy of the defaults) and **raise `"revision"` by 1** each time so running apps pick it up at the next call. Everything below is under `categories` -> the category with `"id": "equipment"` or `"billing"` -> `entry`.

Replace freely (these are the placeholders):
- `entry.items`: the item list. Each item is `{ "id": "...", "label": "..." }`; the label is what the agent sees and what `{item}` prints. Add, remove or reorder items; ids must be unique, start with a letter and use only letters, digits, `-` and `_`.
- `entry.actions[].fragment` (Equipment: `"{action} {qty} {item}. {details}"`; Billing: `"{action} {qty} {item} {details}"`): the sentence for that action. `{action}` = the action label, `{item}` = the item label, `{qty}` = the number the agent typed (empty when none), `{details}` = the text the agent typed (empty when none). Empty ones leave no gap. You may use `{tech.firstName}`, `{tech.id}`, `{job.number}`, `{job.workOrder}`, `{address}`. Only the first character of the whole entry is capitalised and a full stop is added when missing, so write the sentence as it should read.
- `entry.outcomes[].fragment` (Billing): appended after the action sentence. Keep the meaning of the three: only the Completed one may say the work is completed.
- Category `label` and the action/outcome `label`s (what the agent sees on the buttons). The real action names (Added/Removed/Swapped, Added/Removed/Changed) and outcome names (Completed / Requested - not yet completed / Unable to complete) are already the agreed ones; change them only if the business wording changes.
- `entry.qty` (show an optional quantity 1-99), `entry.details` (show an optional free-text box), `entry.outcomeRequired` (agent must pick an outcome; needs at least one outcome).

Do NOT change:
- **ids** of the categories (`equipment`, `billing`), actions, items and outcomes (calls saved in History refer to them; an entry with an id the config no longer has is shown as "no longer available" and left out of the note), and the `kind` (`items`).
- The `{action} {item} {qty} {details} {outcome}` spelling inside fragments (anything else in braces is reported as a warning and printed as typed).
- Keep every action and outcome `fragment` key present (use `""` for no text) and keep at least one action and one item. `outcomeRequired: true` with an empty `outcomes` list makes the whole file invalid.

After saving, the app checks the file on the next call boundary; a file that fails validation is ignored (the app keeps the last good copy and shows the warning chip). A file with only schema warnings (a typo in a `{placeholder}`, an unknown key) is still used, and nothing tells the agent; check new wording in the dev-mode composer warning line (an unknown placeholder stays visible in the note text).
