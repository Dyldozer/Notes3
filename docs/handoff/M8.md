## ICMP_ECHO_REPLY layout used (64-bit)
```
  0 ULONG   Address        IPAddr, network byte order (1.2.3.4 -> 0x04030201); converted back with the same byte swap
  4 ULONG   Status         IP_STATUS (0 = IP_SUCCESS, 11010 timeout, 11002.. unreachable, 11013 TTL expired ...)
  8 ULONG   RoundTripTime  ms
 12 USHORT  DataSize
 14 USHORT  Reserved
 16 PVOID   Data           (8 bytes)
 24 IP_OPTION_INFORMATION  Ttl@24 Tos@25 Flags@26 OptionsSize@27 (+4 pad) OptionsData@32     total 40 bytes
```
Reply buffer = 256 bytes (needs 40 + 32 request bytes + 8 + 16 IO_STATUS_BLOCK = 96). Request data 32 bytes. `IcmpParseReplies` is called once the event is signalled; a count of 0 means the error is the `IP_STATUS` in `GetLastError` (normally 11010). The documented layout is also in the comment above `IcmpBackend`.

## How it works
- **Success** only when the parsed `Status` is 0 **and** the reply address equals the target (checked in `PingRun`, so the mock can simulate it). Anything else is a failed attempt with a plain reason line (`No reply (timed out after 1000 ms)`, `Destination host unreachable`, `Reply from a different address (x) - not counted`, ...).
- **Run status**: `idle|running|succeeded|failed|cancelled|error`. Count mode ends `succeeded` if any attempt got a reply (that is what prefills `reply`), else `failed`. Until-success ends `succeeded` on the first reply, `failed` at the cap. An attempt in flight when the cap is reached is waited for (it may still be a reply); nothing new is sent. `error` is only a local failure (IcmpCreateFile / CreateEvent / Send throwing): it prefills nothing.
- **Timer**: the facade runs one `SetTimer(..., 50)` only while a run still needs ticks; each tick `WaitForSingleObject(event, 0)` per run. Attempts start one `intervalMs` apart (measured from the previous start); an attempt slower than the interval delays the next one (never two in flight). `OnUpdate` fires on each result and once per elapsed second.
- **Cancel**: stops scheduling, status `cancelled` and the console line `Cancelled` are immediate, `OnDone(result)` fires with `Cancelled=true`. The in-flight request is moved to an orphan list; its buffer and event are released only when `Poll` reports completion or `sentAt + timeout + 1000 ms` passed. A request the OS still owns at release time is never freed (it goes to `IcmpBackend.Graveyard`; never seen to happen).
- **Cleanup**: one `IcmpCreateFile` handle per run, `IcmpCloseHandle` once the run is fully drained (finished and no orphan). The facade keeps a cancelled run ticking until drained. `Pinger.Shutdown()` (from `OnAppExit`, registered with `OnExit`) cancels and waits up to 1 s for in-flight requests; anything still pending after that is abandoned without freeing. Closing the window also cancels (`MainWindow.OnClosing`).
- **Prefill**: when a run finishes by itself, `App.PingDone` calls `StaticPrefillPing(cat, AnyReply ? "reply" : "noReply", target)` (unconfirmed, M7 seam) unless the page's target/address changed meanwhile. Cancelled and error runs prefill nothing. Starting a run clears an unconfirmed prefill. Changing the target or the address while running cancels the run (`StaticSet`). New call, Clear All, History load and "Reset category" cancel and forget the run (console, status). Nothing about a run is in the History snapshot.
- **Logging**: debug level only (`ping start`, `ping done`, `ping cancelled`: target IP, mode, counts). Nothing at info; no tech data.

## IMPORTANT finding: keep iphlpapi loaded (cost me most of the time)
`DllCall("iphlpapi\IcmpSendEcho2", ...)` makes AutoHotkey load the DLL for that call and release it again. An asynchronous request completes **later**, inside iphlpapi code on another thread: by then the DLL is gone and the process crashes (event log: `Faulting module iphlpapi.DLL_unloaded`, 0xC0000005); the synchronous `IcmpSendEcho` simply never returned and the async event never fired. Python, PowerShell and ping.exe were unaffected. Fix: `IcmpBackend.Pin()` calls `LoadLibraryW("iphlpapi.dll")` (and `winnsi.dll`, which the ICMP code loads lazily) once per process and never frees them. Without it nothing works under AutoHotkey 2.0.19 here. This is a **must keep** in `_Open`.

## Decisions where the plan was silent
1. **Loopback**: the page's own addresses can never be 127.x (`Ipv4` refuses it), but the task asks to ping 127.0.0.1. `Pinger.Start` refuses 127.x unless `AllowLoopback` is passed; the only callers that do are the selftest and the unit/integration tests, through `App.StartPing(..., {Addr, AllowLoopback})`. `Addr` also makes the run independent of the page's address (selftest only). `CapMs`, `Timeout`, `Attempts`, `Interval` are selftest overrides on `StartPing`; the config bounds still apply to Timeout/Attempts/Interval.
2. **Mixed replies in count mode** end `succeeded` (any reply). Prefill is `reply` when any attempt succeeded, else `noReply`.
3. **Ping and Until buttons are disabled while a run is going** (tooltip "A ping is running. Cancel it first."), so a second click cannot restart. (The facade itself does cancel an old run when a new one starts.)
4. **Wording**: console and status lines as listed above; 0 ms is shown `<1 ms`; unreachable lines name the reporting router when it differs from the target.
5. **Elapsed / cap display** is whole seconds `mm:ss`; a cap shorter than a minute (selftest hook only) shows e.g. `00:01 / 00:01`.
6. **Watchdog**: if a backend never answers, the attempt is counted as a timeout at `timeout + 1000 ms`.
7. A run that ends in `error` shows `Could not ping: <reason>` in the status line and prefills nothing.
8. The outcome picker stays: the agent can still choose the result by hand (and Clear it).
